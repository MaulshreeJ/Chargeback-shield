# Chargeback Shield

![Tests](https://github.com/MaulshreeJ/Chargeback-shield/actions/workflows/tests.yml/badge.svg)

**Razorpay AI Buildathon 2026 — Track 02, AI Risk Manager**
Loss class: **chargeback / friendly-fraud disputes** (one class of loss, per the track brief).

🔴 **Live demo:** https://chargeback-shield-6egu.onrender.com/
*(free-tier hosting — if it's been idle it can take 30-60s to wake up on the first request; give it a moment)*

Chargeback Shield does two things, deliberately kept separate:

1. **Predicts** which transactions are at elevated risk of a future dispute,
   before any dispute is filed — so a merchant can take a cheap preventive
   step (confirmation email, short settlement hold) instead of guessing.
2. **Responds** when a dispute *is* filed: assembles exactly the evidence a
   card network's reason code requires, and recommends fight / concede /
   review under a fixed, auditable policy — never an LLM guess.

Every score and every packet decision is written to an append-only audit
log (`reports/audit_log.jsonl`), so any single decision can be pulled back
up and inspected after the fact — try it live: score a transaction, then
look up its audit ID.

## Why this and not generic fraud detection

Pre-authorization transaction-fraud scoring — "is this swipe fraudulent
right now" — is the obvious build for this track, and a crowded lane
(see `ARCHITECTURE.md` for how this compares to other public approaches).
Chargeback Shield scores a different point in the payment lifecycle
instead — the dispute itself — and pairs the prediction with an automated
*response*, which is closer to what the track brief actually asks for
("fraud detection, verification, or automated response systems"). Before a
dispute is filed, we're the early-warning system; after it's filed, we're
the evidence assembly line. Nothing else in this track does both halves of
that lifecycle in one system.

## Honesty about the data

**All data is synthetic**, generated by `src/data_gen.py` from documented
correlates of friendly fraud (digital goods with no delivery confirmation,
cross-border mismatches, subscriptions, oversized first purchases, repeat
disputers, merchant-level heterogeneity) plus noise. It is not fit to, or
derived from, any real Razorpay or cardholder data. Every metric below
should be read as a demonstration of *methodology*, not a claim about
real-world performance — see `reports/model_card.md` for the full
disclaimer and the complete precision/recall tradeoff curve (a single
flattering number is easy to cherry-pick; the full curve, generated
alongside it, is not).

## Results (held-out test set, synthetic data)

At the shipped operating threshold: **40.0% precision, 40.6% recall**.
Compared against the simplest rule you could write by hand — "flag if
digital good with no delivery confirmation" — which gets **25.6%
precision, 23.9% recall**. So the model is a real, checkable improvement
over the obvious guess, not a black box asking to be trusted on faith —
both numbers are computed on the same held-out fold, and you can pull the
live version of both from `GET /metrics` on the demo above right now.

The 40% precision floor was a deliberate business choice, not the best
number available: the action on a flagged transaction is a cheap email or
short hold, not a decline, so recall was worth trading for. The model card
also reports a **cost-based alternative operating point** — what threshold
minimizes total assumed cost instead of targeting a precision floor — and
is explicit about why the shipped default doesn't just use that number
instead (see `ARCHITECTURE.md`, "Cost-based (expected-value) thresholding").

None of these numbers are hardcoded here — `reports/metrics.json`,
`reports/model_card.md`, and `reports/packet_metrics.json` regenerate
fresh every time the pipeline below runs, so this README can't go stale
relative to the actual model.

## Quickstart

```bash
python -m venv .venv && source .venv/bin/activate   # optional
pip install -r requirements.txt

# 1. Generate synthetic data, train the model, write metrics + model card
python -m scripts.train

# 2. Evaluate the evidence-packet engine over the same synthetic disputes
python -m scripts.evaluate_packets

# 3. Build the merchant-level dispute-ratio rollup
python -m scripts.merchant_rollup

# 4. Run the test suite
pytest -q

# 5. Run the API + dashboard
uvicorn src.api:app --reload
# open http://127.0.0.1:8000/  -- a live dashboard: model metrics, the
# precision/recall tradeoff table, the evidence-packet engine's batch
# results, the merchant risk rollup, and interactive forms to score a
# transaction, generate an evidence packet for a sample dispute, and look
# up its audit record.
#
# Raw JSON API, if you'd rather script against it directly:
# POST /score, POST /disputes/packet, GET /audit/{id}, GET /metrics,
# GET /packet-metrics, GET /sample-disputes, GET /merchants/rollup
```

## Docker

```bash
docker build -t chargeback-shield .
docker run -p 8000:8000 chargeback-shield
# open http://127.0.0.1:8000/ -- the model and all reports are trained/
# generated at build time (100% synthetic data, no secrets needed), so the
# container starts up instantly. The optional Gemini narrative layer still
# reads GEMINI_API_KEY from the environment at *runtime* if you want it:
# docker run -p 8000:8000 --env-file .env chargeback-shield
```

This is exactly how the live demo above is deployed (Render, building
straight from this Dockerfile on every push).

## Explainability

`POST /score` returns `top_factors`: the 2-3 features that most moved
*this specific* prediction, via occlusion (compare the real prediction to
one where a feature is swapped for its typical training-set value). No
extra dependency, and it's shown live on the dashboard under "Why". The
model card also reports the naive one-rule baseline next to the trained
model's numbers (see Results above), so the model's actual lift is
checkable rather than asserted.

## Merchant risk rollup

`GET /merchants/rollup` (dashboard section 6) surfaces which merchants are
chronically high-risk, computed over full merchant history — distinct
from the leakage-safe `merchant_dispute_rate_90d` feature the model
actually trains on (which only ever sees a merchant's history up to that
point in time; see `ARCHITECTURE.md`'s "Merchant-level risk pooling" for
the honest caveat on how that feature's signal was introduced).

## Project layout

```
src/
  schemas.py          pydantic contracts (Transaction, Dispute, EvidencePacket, ...)
  data_gen.py          synthetic transaction + dispute generator (ground truth)
  features.py          shared feature engineering (training + live API)
  model.py             HistGradientBoosting risk model, train() + RiskModel
  evidence_engine.py   reason-code -> evidence map, deterministic fight/concede/review policy
  narrative.py         optional, cosmetic-only LLM narrative layer (see below)
  audit.py             append-only JSONL audit trail
  api.py               FastAPI surface
scripts/
  train.py             generate data (if needed) -> train -> metrics.json + model_card.md
  evaluate_packets.py  evidence-engine batch evaluation -> packet_metrics.json
  merchant_rollup.py   merchant-level dispute-ratio rollup -> merchant_rollup.json
tests/                 pytest suite for the model and the policy engine (23 tests)
reports/               generated: model.joblib, metrics.json, model_card.md,
                       packet_metrics.json, merchant_rollup.json, audit_log.jsonl
```

## Optional LLM narrative layer

`src/narrative.py` can draft a 2-3 sentence human-readable summary of a
dispute packet via the Gemini API, purely as decoration on top of
`evidence_engine`'s decision — it cannot change the recommendation,
invent evidence, or alter completeness/confidence. Configure it via a
local `.env` (see `.env.example`; **never commit `.env`**):

```
GEMINI_API_KEY=your-key-here
GEMINI_MODEL=gemini-2.0-flash   # override if this model name changes
```

If the key is missing, the network call fails, the model name is wrong,
or the request is rate-limited, `draft_narrative()` catches it and
returns `None` -- the API falls back to the deterministic `rationale`
string, and the packet is always complete and usable either way. This
isn't a hypothetical: **the live demo above currently returns
`"narrative": null`** on every packet, even with a key configured, and
every packet still comes back with a correct completeness score,
recommendation, and rationale regardless. That's the point of keeping
this layer optional and separate from the policy engine, rather than a
gap worth hiding.

## Known limitations & what's next

- Synthetic data can't capture real adversarial adaptation -- fraud
  patterns that shift in response to the model existing.
- Evidence retrieval is currently simulated (`generate_evidence_store` in
  `src/api.py`). A real deployment would call Razorpay's own systems of
  record here -- transaction, customer, delivery, and payment evidence --
  without changing the policy layer itself: prediction, policy, evidence,
  and audit are already separated (`ARCHITECTURE.md`), so this is an
  integration, not a research problem.
- The optional narrative layer is unverified end-to-end in this
  environment (see above) -- cosmetic only, and the system is designed to
  not depend on it.
